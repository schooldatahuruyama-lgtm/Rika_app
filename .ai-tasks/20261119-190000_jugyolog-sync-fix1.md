## 変える内容

### 指摘 1: 古い状態からの上書きを止める（`js/sync.js`）

授業ログ側の規則が、次のように変わる（この指示書と同時に直している）。

- `rika/state/<uid>` の形: `{ v: 1, updatedAt: 数, json: 文字列, base: 数（あってもなくてもよい） }`。
- すでに値があるとき、書きこみが通るのは **`base` が今の `updatedAt` と同じ** で、**新しい `updatedAt` が今の `updatedAt` より大きい** ときだけ。ちがうと「権限がありません」（401／403）。
- 値が無いとき（初めて）は、`base` は要らない（付けない）。

`push` の state の書きこみを、次に変える。

1. `seenRev` が数なら `base: seenRev` を付けて PUT。`seenRev` が `null`（リモートにまだ無いと分かっている）なら `base` を付けない。`updatedAt` は `max(now(), seenRev + 1)`。
2. 拒まれた（`denied`）ら、**ほかの端末が先に書いた**かもしれないので、`pull` と同じ取りこみ（state を読み、かたまりを取りこみ、`mergeRecord` で合わせる）を行い、合わせた結果で 1 からやり直す。やり直しは 1 回の `push` につき 2 回まで。
3. 読み直しても `updatedAt` が `seenRev` と同じ（＝だれも書いていないのに拒まれた）なら、本当に書けない → `denied`。
4. やり直しを使い切ったら `'offline'`（次の機会にまた試す。送っていない分は残す）。
5. `push` が入れ物を合わせ直したときは、呼び出し側が入れかえられるように、`push` の戻り値を `{ status, store, changed }` に変える（`pull` と同じ形）。`js/app.js` は、`changed` のとき `pull` のときと同じ扱い（入れかえて保存、作り直してよい画面なら作り直す）をする。
6. `seenRev` が `null` で、リモートに state があるかどうか分からないとき（読めないかたまりがあって `seenRev` を進めていない場合など）も、state を書く前に必ず state を読み、今の `updatedAt` を `base` にする。

### 指摘 2・3: 同期の情報を、記録と一緒に保存する（`js/sync.js`・`js/app.js`）

- 同期の情報（`seenRev`・`chunks`・`len`・`pending`・`sending`・`dirty`）を、別のキー `rika-quest:sync:<uid>` に置くのをやめ、**アカウントの入れ物（`rika-quest:acct:<uid>`）の中の `sync` という項目**に置く。入れ物と同期の情報は、いつも 1 回の `setItem` で一緒に書く（片方だけが残る・消えることが無い）。
  - `js/storage.js` の `parseStore` は知らない項目を残すので、変えなくてよい。`singleStore`・`normalizeStore`・`claimRecord`・`pull` が作る新しい入れ物など、入れ物を作り直す所で `sync` を落とさないこと。
  - `packState`（リモートへ送る中身）には `sync` を入れない。「記録を書き出す」のファイルにも入れない（書き出す前に外す）。
- `createSync` は、保存場所に自分で書かない。入れ物の保存は、引数で受け取る `save(store)`（保存できたら `true`）で行う（`js/app.js` が、今ある `RQ.storage.save` を使って渡す）。
- `capture` は「保存の前」に呼ぶ形に変える: `js/app.js` の `save()` は、アカウントモードなら **先に** `sync.capture(今の入れ物)` で入れ物の中の `sync` を進め、**そのあと 1 回だけ**入れ物を保存する。保存に失敗したら、`sync` の進みはメモリに残るだけでよい（次の保存でまた書かれる）。
- 送るとき（`prepareChunk`）: `sending`（id と中身）を入れた入れ物の**保存が成功したときだけ**、そのかたまりを送る。保存に失敗したら送らず、`'offline'` を返す（`pending` はそのまま）。state の書きこみのあと・かたまりの送信のあとの保存に失敗しても、例外で止めない（次の `push` で、同じ id のかたまりは「拒まれて中身が同じなら成功」になり、state は `base` のやり直しで直る）。
- 古いキー `rika-quest:sync:<uid>` が端末に残っていたら、見つけたときに消す（まだ公開していないしくみなので、中身の引きつぎは要らない）。`config.link.syncKeyPrefix` は、その片付けのためだけに残す。
- ほかのアカウントの入れ物の片付け（`cleanAccounts`）は、入れ物の中の `sync` を見て「送っていない分が無い」ものだけ消す。`sync` が無い・読めない入れ物は消さない。
- 入れ物が壊れていて退避されたとき（`RQ.storage.load` の今ある扱い）は、空の入れ物と空の `sync` から始まり、`pull` でリモートの state と**すべてのかたまり**を取りこむ（`chunks` が空で履歴も空なので、二重にならない）。

### 指摘 4: モードを切りかえるとき（`js/app.js`）

- 端末モードへ切りかえる（`useDevice`）・読みこみ直す（`loginChanged`）前に、**今の入れ物（持ち主）に対して**学習の途中の保存（`saveBeforeReload` の中身）を済ませ、そのあとで `state.session`・`state.lastResult` など、学習の途中の状態を空にする。空にしてから入れ物を入れかえる。
- `saveBeforeReload` は、学習の途中の状態が「今の入れ物の今のプロフィール」のものだと分かるときだけ書く（学習を始めたときのアカウントの uid（端末モードなら `null`）とプロフィールの id を覚えておき、ちがえば書かない）。

### 指摘 5: 帯の文（`js/app.js`）

通信できないことと、送っていない分があることを分ける。

| 場面 | クラス | 文 |
|---|---|---|
| アカウントモードで、通信できず、送っていない分がある（`sync.isDirty()` が真） | `is-wait` | まだ送れていない記録が N 件あります。電波のよい所で開くと、自動で送ります。（履歴の件数が 0 で、設定などの変更だけのときは「まだ送れていない記録があります。…」） |
| アカウントモードで、通信できないが、送っていない分は無い | `is-wait` | 通信できません。送っていない記録はありません。学習は、このまま続けられます。 |

ほかの帯は変えない。今あるテストで、まちがった文を期待している所は直す。

## 端の場合

- 不正な入力: 入れ物の中の `sync` の形がちがう（数でない `seenRev`・配列でない `chunks` など）→ リモートを正として扱う: まず state を読む。リモートに state がある → `sync` を空（`seenRev: null`・`chunks: []`・`len` は 0・`pending` は空）にし、**ローカルの history・xpLog を空にしてから**、すべてのかたまりを取りこみ直す（二重を防ぐため。state の合わせ方は今までどおり）。リモートに state が無い（`none`）→ 捨てず、ローカルの history・xpLog の全部を `pending` に入れて送る。通信できないあいだは、何も捨てない・送らない。
- 重複と境界: 2 台が同じ `base` で同時に書いたら、片方だけが通る。通らなかった方は読み直して合わせ、もう一度送る。`base` のやり直しは 2 回まで。
- 違反や失敗の見せ方: 帯の表のとおり。端末に保存できないときは、今ある右上の「保存できません」と、帯の「まだ送れていない記録…」で知らせる。
