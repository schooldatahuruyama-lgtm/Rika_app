## いちばん大事なこと（著作権と利用規約）

- ちびむすドリル（パディンハウス）の利用規約は、教材の**改変・部分使用・デジタル配布・アプリ開発への利用を禁止または要連絡**としている。だから **プリント（PDF）の文・図・解答は見ない・写さない・言いかえない**。
- 使ってよいのは、公開ページに出ている **テーマ名・説明文・枚数だけ**（下の材料）。それを「どの内容をどのくらいの厚さで出題するか」の目安にし、**問題・解説・カード・図はすべて中学理科の知識から自作する**（学習指導要領の範囲。教科書名・出版社名・ちびむすドリルの名前は書かない）。
- アプリに入る文章に、プリントの文章と同じ文が入ってはいけない（見ていないので入りようがない。もし知っている文があっても書かない）。
- 報告には「参考: ちびむすドリルのテーマ名」だけ書く（URL も PDF 名も書かない）。

## 反映の形（決めたこと）

1. 各単元に**領域「ドリル」**（`id: '<単元id>-drill'`、`title: 'ドリル'`、`free: true`、`order` は既存の最後＋1）を足す。その中に、担当表のテーマごとにステージを置く。
   - ステージ id は `<単元id>-dr<n>`（n は担当表の番号）。`title` は「ドリル n: <内容>」（例「ドリル 1: 身のまわりの物質の性質」）。`minutes` は 5〜7。
   - 枚数が 5 枚以下のテーマは 1 ステージ、6 枚以上は 2 ステージ（担当表に書いてある）。2 ステージのときは内容を前半・後半に分ける（例: 電流と電圧Ⅰ → 回路と電流計／電圧とオームの法則）。
2. ステージの中身: `lessons` 2〜3 枚（40〜160 字、用語は `**語**`、図は汎用の部品で簡単に。写真・anim は足さない）、`warmup` 1 問（choice。予想や日常の場面）、`problems` 6 問（うち **1 問は `term: true` の用語問題**、**1 問以上は figure-choice か drag**、1 問以上は数値や表を読む問題か計算の問題（そのテーマにあれば））、`retryPool` 4 問以上（concepts に書いた各概念に 2 問以上。用語問題を 1 問）。
3. **既存の問題と同じ問いをくり返さない**。同じ単元の `docs/reports/content/<単元>.md` を見て、既にある問いは角度を変える（別の場面、別の数値、理由を問う、誤りを探す、表から読む、順に並べる など）。説明文に出てくる内容で、既存の教材にないもの（例: 力の「張力・抗力・静電気力」、気象の「雲量・風向・風速・降水量」、「イオン化傾向」、「水圧」）を優先して出す。
4. 概念: **既存の概念 id を使う**（担当表の単元の概念一覧を見る）。新しい概念は足さない（どうしても既存で表せないときだけ足し、`checkPool` 3 問以上・`basic`・`lessonStageId` を付け、報告に理由を書く）。
5. 数値の問題は `fill` の `number`（`tolerance` は割り切れるなら 0、割り切れないときは 0.1。`unit` に単位）。中学理科の単位と有効数字。
6. 問題文（`prompt`）は **120 字以内**（ライブクイズでも出せるように）。figure-choice の `region` は **2〜8 個**、`r` は 22 以上、`label` か `name` にア・イ・ウ…（並び順をア→イ→ウにする）。図は 320×240、文字 12px 以上。
7. 図から選ぶ問題は、図だけに頼らず `prompt` にア・イ・ウの意味を書く。drag は `samples.correct`/`samples.wrong`（wrong は 40px 以上はなす）。
8. id: 問題 `<単元id>-dr<n>-p<k>`（用語 `-t<k>`、warmup `-w1`、retryPool `-r<k>`）、カード `<単元id>-dr<n>-c<k>`。既存の id と重ねない（`tests/content-all.test.js` が全単元で一意を検査）。
9. `docs/reports/content/<単元>.md` に、新しい領域の節を既存のミニプリントの節と同じ形で足す（冒頭に追加の 1 行、各ステージのカードの要旨、問題の表 `id | 形式 | 概念 | 内容【正解】`、「参考: ちびむすドリル【テーマ名】」、末尾に「自信のない点（先生に確認してほしい）」）。

## 端の場合（必ずこのとおりに）

- 数の答え: `number` の `answer` は数（文字列にしない）。小数は割り切れる桁まで。負の数・分数の答えは出さない（割り切れない商は小数第 1 位まで、`tolerance: 0.1`）。
- 単位: `unit` に書き、`prompt` の中に「〜 cm で答える」のようには書かない（アプリが単位を添える）。
- 語の答え（`word`）: 語群は 3 つ程度、正解はそのうち 1 つだけ。表記ゆれ（例: 「はね返る／はねかえる」）が正解になる語は語群に入れない。
- 選択肢: 3〜4 つ。正解は 1 つだけ。「すべて正しい」「どれでもない」は使わない。選択肢の文は 30 字以内。
- 図から選ぶ: 正解の region は 1 つ。region が重ならない（中心の距離 ≥ 2r）。
- drag: `target` は図の中（0 ≤ x ≤ 320、0 ≤ y ≤ 240）。`samples.wrong` は意味の上でも誤りの位置。
- 空欄: `fill` の `text` には `[b1]` を 1 つだけ（空欄 2 つの問題は作らない。ライブクイズの自由記述に取りこめるように）。
- 重複: 同じ単元の既存の問題と `prompt` が同じ・ほぼ同じものを作らない。1 ステージの中で同じ答えの問題を 3 問以上並べない。
- 失敗したときの見せ方はアプリ側の決まりどおり（`explanation` は責めず次の一歩）。赤い大きな × や減点の表現を書かない。

## 守ること

- 編集してよいのは **担当の `content/<単元>.js` と `docs/reports/content/<単元>.md`、自分の報告ファイルだけ**。`content/readings.js`・`js/*`・`index.html`・`sw.js`・`tests/*`・ほかの単元は触らない。
- 既存のステージ・概念・問題・カードは変えない（`git diff` は追加だけになる）。
- `npm test` を実行し、担当の単元に関する失敗がないこと。ただし `tests/ruby.test.js` の「網羅率」の失敗（ふりがなの辞書にない語）だけは許容する（辞書は controller があとで足す）。`node tools/ruby-missing.js --all` の出力のうち自分の単元の語を報告に書く。
- 自分のポートの `python -m http.server <ポート>`（8870 番台から担当番号を足す。例: 担当 3 → 8873）を起動して、headless Edge か Playwright があればそれで、新しいステージを 1 つ以上、解説→問題→結果まで通す（内蔵ブラウザのタブは使わない。使えなければ node で `validateUnit` と `tests/content-all` の成功をもって代える、と報告に書く）。
- git 操作なし（commit・add・checkout）。ネットワークからパッケージを追加しない。サブエージェントなし。**ちびむすドリルのサイトへアクセスしない**（PDF を開かない）。
